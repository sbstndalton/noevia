# Run plan — issue #264: qualify Deep Research on a sandbox model before admin rollout

## Host
DaServer (Unraid), public URL `https://noevia.daserver.work`. Sidecars per `docs/deployment.md`:
`cowork-web-1`, `cowork-diary-1`, `cowork-ocr-1`, native llama.cpp (Vulkan), CPU embeddings,
kiwix, model-loader, code-sandbox, docling, CPU-only Laya. Per `docs/spec-deep-research.md`'s own
prior gate run: executed **from inside the web container** against the native llama.cpp endpoint,
"outside backup and mover windows, detached."

## Configuration
- Containers: `cowork-web-1` only (runs the harness script); reads/writes go to the local llama.cpp
  server already running natively on the host (not a new container). No Diary, OCR, or code-sandbox
  container involvement.
- Env: `RESEARCH_BASE_URL`, `RESEARCH_MODEL`, optionally `RESEARCH_VARIANTS` (names only, per
  `experiments/deep-research/README.md`). `NOEVIA_FEATURE_DEEP_RESEARCH` stays `"false"` in the
  live `.env` (per `docs/spec-deep-research.md`'s 2026-09-17 decision record) — this run does not
  flip it. No admin UI is touched.
- Model / GPU / VRAM: the prior run used **Gemma 12B Q4 QAT (owner decision 2026-09-25; replaces the Ornith-1.5-9B-Q5_K_M used in the prior gate)**, ctx 16384, llama.cpp b10920,
  `--models-max 1` (single model slot). `docs/research/system-one/05-model-residency.md` /
  `13-model-classes...md` note DaServer's CPU+iGPU share one 29GB pool and llama.cpp is capped at
  14GB — one model at a time. **Open question:** which "sandbox model" the owner wants this run to
  use is not fixed in the issue; the previous gate's single-model-slot constraint caused the prior
  run's failure (a Nextcloud Assistant test evicted the 9B mid-run). This plan proposes reusing the
  same model class unless the owner names another, and explicitly recommends **disabling
  Nextcloud Assistant / any competing inference use for the run's duration** to avoid a repeat.

## Cases / fixtures
Synthetic only, already built: `experiments/deep-research/fixtures.json` — a static fixture site
with invented facts served on `127.0.0.1`, 12 questions (4 requiring project notes) + 2 adversarial
pages, matching `docs/spec-deep-research.md` §8. Never the real Diary corpus or real user
prompts/projects. Variants A (chat+search baseline), B (pipeline, no plan), C (pipeline + plan).

## Memory and duration estimate
- Basis: the 2026-09-17 gate run recorded per-variant median times of 11.8s (A), 51.1s (B), 225.6s
  (C) per question, across 8 clean questions (of 12+2 planned) before a model eviction stopped it.
  Extrapolating to all 14 fixtures across three variants: roughly (11.8+51.1+225.6)s × 14 ≈ 68
  minutes of model wall time, plus overhead for restarting the model and any manual review —
  budget **~2 hours** total, run detached (`nohup … &`) as before.
- Memory: one 9B-class Q5 GGUF loaded in the shared 29GB pool (llama.cpp capped at 14GB per the
  residency doc), no VRAM headroom for a second model — hence the single-slot risk above.

## Impact on live users
- The prior run's own failure mode is the impact risk: with `--models-max 1`, only one model can
  be loaded at a time, so **any other live inference (chat, Nextcloud Assistant, embeddings-backed
  RAG that needs the same slot) is paused or will contend for the slot** for the run's ~2 hour
  duration. Deep Research itself stays behind the `deepResearch` flag (off), so ordinary chat
  users could still be degraded if their request tries to use the same loaded model and finds it
  busy or gets evicted (as happened in the 2026-09-17 run). No model needs to be manually unloaded
  beforehand — the harness loads its own model — but the owner should schedule this at low-traffic
  time and confirm no other maintenance (backup, model tuning window) overlaps.

## Smoke test that runs first, and its pass criterion
Run **Q1 of variant A only** first (single chat-style call over the fixture site) before the full
harness. **Pass criterion:** the process reaches `RESEARCH_MODEL` successfully (no `HTTP 500`/
connection error), returns a report referencing fixture content, and the deterministic citation
checker in the harness runs without throwing. If this single-question smoke fails (e.g. model not
reachable, wrong port), stop before spending the full ~2 hour budget.

## Outputs and where they are stored
Per question: required facts covered, adversarial compliance (forbidden strings present — must be
0), deterministic citation validity, web calls, wall time — written to the redirected results file
(e.g. `/tmp/deep-research-gate-<date>.txt`) inside the container; copy it out via `docker cp` for
the record. The spec's own §8 table should be updated in `docs/spec-deep-research.md` with a new
dated "Gate result" section, same format as the existing 2026-09-17 one. No project files, no
`Research/*.md` are saved anywhere since `NOEVIA_FEATURE_DEEP_RESEARCH` stays off and this harness
runs standalone, not through the app's save-to-project path.

## Pass/fail criteria (from issue's "Done when")
- A reproducible evaluation and pass/fail criteria are recorded (reuse §8 of
  `docs/spec-deep-research.md`: adopt B or C only if it covers materially more required facts than

## Rollback / off switch
`NOEVIA_FEATURE_DEEP_RESEARCH` is already `"false"` in the live override and is not touched by
this run. If the run leaves the loaded model in an unexpected state, restart the native llama.cpp
service normally (no compose change). No `.env` backup is needed since no `.env` edit occurs.
