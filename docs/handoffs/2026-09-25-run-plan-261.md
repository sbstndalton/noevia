# Run plan — issue #261: review System-One decision logs after a week of live use

## Host
DaServer (Unraid), public URL `https://noevia.daserver.work` (Cloudflare tunnel). Compose project
"Cowork". Sidecars per `docs/deployment.md`: `cowork-web-1`, `cowork-diary-1`, `cowork-ocr-1`, plus
native llama.cpp, CPU embeddings, kiwix, model-loader, code-sandbox, docling, and CPU-only Laya
(`cowork-laya`). This is a **read-only review of an existing log file** — no new container, no
image build.

## Configuration
- No new containers. Reads the file `system-one-decisions.jsonl` (+ `.1` rotation) that
  `apps/web/server/decision-log.cjs` already writes into the web container's `DATA_DIR`
  (`apps/web/server/ui-data` in dev; the live mount under `/mnt/docker/appdata/cowork/...` per
  `.env` — confirm exact path with `docker inspect cowork-web-1` before running).
- Env: no new env vars. Existing flags already in effect and unchanged: `NOEVIA_FEATURE_...`
  (`systemOneRouting`, `stepSupervision` — see `apps/web/server/features.cjs`).
- No GPU/VRAM use: this is a log summarize step, no inference.
- Tooling: `node apps/web/server/decision-log.cjs <dir>` (built-in CLI, `require.main === module`
  branch) prints `summarize()` — counts by `selected`/`action`, `fellBack`, and margin buckets.
  No model call.

## Cases / fixtures
None needed — the log already contains a week of real production routing/supervision decisions.
Per `decision-log.cjs`'s own design, entries are **text-free**: no prompt content, no message
text, only `kind`, `selected`/`action`, `margin`, `fellBack`, timestamp. This satisfies the "no
prompt content" requirement in the Done-when criteria directly, since the log format already
excludes it. If a rerun of the System-One probe is judged necessary (only if Laya or role labels
changed — see below), that reuses the existing synthetic-only probe: `apps/web/scripts/
system-one-probe.cjs` against `apps/web/scripts/system-one-probe-heldout{,2,3}.json`. Never the
real Diary corpus or real chat prompts.

## Memory and duration estimate
- Log read/summarize: milliseconds, negligible memory (a Node script reading a <1MB JSONL file;
  `decision-log.cjs` caps each file at `maxBytes = 1MB` with one rotation, so at most ~2MB read).
  Basis: `createDecisionLog({ maxBytes = 1024*1024 })` in the source.
- If a probe rerun is needed: basis is the existing measured runs in
  `docs/research/system-one/19-routing-labels.md` — median 0.45–0.6s per decision, ~90 decisions
  total across the three held-out sets, so under 2 minutes wall time, no meaningful memory beyond
  the already-resident Laya process (~0.5–2GB, already loaded live).
- Total estimated duration: under 10 minutes including manual review of the summary and drafting
  the report comment.

## Impact on live users
- Reading the log file and running `decision-log.cjs`'s summarizer touches nothing live: no
  service restart, no model load/unload, no route change. Zero impact expected.
- If a probe rerun against Laya is judged necessary: Laya already serves production routing
  decisions at ~0.5s each; a handful of synthetic extra calls add negligible queueing. No model
  must be unloaded — Laya is CPU-resident and independent of the GPU-loaded chat model. No
  planned Done-when requires a rerun; the issue explicitly says "Rerun the System-One probe only
  if Laya or role labels change" — confirm neither changed before running it.

## Smoke test that runs first, and its pass criterion
Before summarizing: confirm the log file exists and is non-empty and that `docker ps` shows
`cowork-web-1`, `cowork-laya` (or whichever container holds `DATA_DIR`) healthy with an uptime
≥ 7 days (or note the actual observation window if the container restarted, since a mid-week
release resets nothing in the log file itself but a host-level restart could shorten the sample).
**Pass criterion:** `wc -l system-one-decisions.jsonl* ` returns at least a few dozen rows, and
`node decision-log.cjs <dir>` runs without error and returns valid JSON.

## Outputs and where they are stored
- The `summarize()` JSON (counts, fallback rate, margin buckets) — pasted into the issue #261
  comment and into `docs/roadmap.md`'s finding link, **no prompt content**, per the issue.
- If any representative failure classes are described, they must be described by decision kind
  and margin bucket only (e.g. "3 near-tie route misses, margin 0.05–0.1"), never by quoting the
  underlying message.
- No new file is committed to the repo unless the owner wants a permanent doc; the natural home
  would be a new dated section under `docs/research/system-one/` (e.g.
  `20-week-one-live-review.md`), following the existing numbering pattern, only if the owner asks
  for it kept as a doc rather than just an issue comment.

## Pass/fail criteria (from issue's "Done when")
- The observation window, counts, fallback rate, and representative failure classes are recorded
  without prompt content.
- Any proposed tuning has held-out probe evidence (i.e., cite an existing or newly-run held-out
  set); otherwise the explicit decision is "keep current routing."
- The roadmap links the finding.
- No routing change is bundled into this ticket — this plan produces a report only, never a
  code/config change.

## Rollback / off switch
Not applicable — no config, code, or running state is changed by this plan. If a probe rerun were
somehow to trip the Laya circuit breaker (3 consecutive deadline misses bench it for 60s per
`19-routing-labels.md`), the existing fallback (legacy classifier) already covers that
automatically; no manual rollback needed.
