# Run plan — issue #518: persona-swap KV-cache study (prefix layout, slot reuse, TTFT)

Part of the local multi-agent milestone (#511, M7). This plan is what the owner approves before
any real run. The harness (`experiments/persona-kv/study.cjs`) is offline-tested only; **nothing
has been measured yet** and no number in this document is a result.

## Question
When one local model serves four personas (Astra planner, Sol executor, Jev verifier, Luna
reviewer) through a single llama.cpp slot, what does a role switch cost?
1. Persona placed **after** a stable shared prefix vs placed **at the start** of the prompt.
2. llama.cpp slot **save/restore** (`/slots/{id}?action=save|restore`) vs a cold full prefill.
3. Time to first token (TTFT) and prompt tokens actually evaluated (`timings.prompt_n`) vs served
   from cache (`timings.cache_n`) per switch.

## Host
DaServer (Unraid, 10.69.0.130). The study runs from any machine that can reach the native
llama.cpp HTTP endpoint; the harness is plain Node and only talks HTTP. Owner chooses the
invocation host (for example `docker exec` into `cowork-web-1`, same access pattern as #264/#265,
or the Mac over the LAN). No new container, no install.

## Model (owner to choose)
**Not chosen here.** The owner picks one already-qualified preset (docs/deployment.md lists the
qualified 32,768-context/one-slot presets). Recommendation for the first smoke: the smallest
qualified preset. The model must already be loaded and serving; the harness never loads,
unloads or reconfigures models.

## Preconditions
- llama.cpp started with **`--slot-save-path <dir>`** (slot files are written there). Without it
  the two restore arms are recorded as `slot-save-unavailable` and skipped; the layout arms still
  run. Enabling that flag is a **server configuration change the owner performs**, not the harness.
- `--parallel`/slots: the study drives slot 0 only (`--slot-id`). Confirm `total_slots >= 1`
  (harness reads `/props` and aborts if the slot does not exist).
- Prompt cache must be enabled (the llama.cpp default); requests send `cache_prompt: true`.
- **Pause all other inference** for the run: chat, RAG rerank, embeddings-through-llama.cpp, and
  the #264/#265 live passes. Any other request to the same slot evicts the cache and invalidates
  TTFT. DaServer has one model slot shared with noevia chats (deployment.md), so this is a
  maintenance window with live chat degraded or unavailable.
- **Avoid backup and mover windows** (Unraid mover, Nextcloud/appdata backups, parity checks).
  They contend for disk and CPU and would add noise to TTFT and slot-file write/read times.
- Free disk under `--slot-save-path`: see memory impact below.
- Nobody edits `models.ini` or restarts the model manager during the run.

## Configuration under test
Five arms, each repetition runs the fixed 8-step role sequence
`astra, sol, jev, luna, astra, jev, sol, luna` (all synthetic tasks and personas, see
`experiments/persona-kv/fixtures.cjs`):

| Arm | Layout | Slot handling before each request |
|---|---|---|
| `cold` | persona after prefix | erase slot (full prefill; the baseline) |
| `persona-first` | persona then prefix | none (prompt cache only) |
| `after-prefix` | prefix then persona | none (prompt cache only) |
| `restore-prefix` | prefix then persona | restore a saved prefix-only state |
| `restore-persona` | prefix then persona | restore that persona's saved state on revisits, else the prefix state; save after a persona's first use |

Reported per arm: TTFT mean/median/p95, switch time (restore + TTFT), prompt tokens evaluated,
tokens from cache, cache-reuse ratio, speed-up versus cold, and a revisit-only table. Step 0 of
each repetition (the first fill) is reported separately from role switches.

## Exact commands
Run from the repository root; `<url>` is the llama.cpp base URL (no path), e.g. `http://127.0.0.1:8080`.
```sh
# 0. Plan only. No network, no approval flag needed. Prints the full request matrix.
node experiments/persona-kv/study.cjs --dry-run --base-url <url>
node experiments/persona-kv/study.cjs --dry-run --base-url <url> --smoke

# 1. Smoke test first (needs approval): 1 repetition, 3 steps, 4-paragraph prefix, all five arms.
node experiments/persona-kv/study.cjs --i-have-approval --smoke --base-url <url> --out <dir>/smoke

# 2. Full run, only after the smoke passes and the owner approves again.
node experiments/persona-kv/study.cjs --i-have-approval --base-url <url> --out <dir>/full \
  --repeats 3 --prefix-paragraphs 40 --n-predict 8
```
Without `--i-have-approval` the harness refuses (exit 2). Optional `PERSONA_KV_API_KEY` supplies a
bearer token; the URL must not embed credentials.

## Smoke test and pass criterion
Step 1 above. **Pass:** exit 0; `summary.md` shows all five arms with `Errors = 0` and no
`skipped`; `cache_n` and `prompt_n` are non-null in `results.json` (server returns `timings`);
`restore-prefix` shows `restored.nRestored > 0`; `after-prefix` shows non-zero cache reuse on
switches. If the restore arms are skipped, stop and fix `--slot-save-path` before the full run;
if `timings` are null, the llama.cpp build does not report them and the study cannot answer
question 3. Smoke needs about a minute and 38 HTTP calls.

## Duration and memory impact (estimates by construction, unmeasured)
- Full run (3 repeats): 5 arms x 3 repeats x (8 steps + setup) = 233 HTTP calls (the dry-run reports it), of which
  about 135 are 8-token completions. Cold and persona-first steps prefill the whole prompt (about 1,100
  tokens at 40 paragraphs). Wall time is dominated by prefill: roughly 120 x (prefill of about
  1k tokens + 8 decode tokens). At a few hundred tokens/s prefill that is on the order of
  **5–15 minutes**; on slower CPU/iGPU prefill it could reach **30 minutes**. Request
  timeouts are 120 s each (`--timeout-ms`, max 300 s), hard call cap 5,000, repeats max 10, abort
  after 3 consecutive request errors.
- Memory: no extra model is loaded; KV cache stays within the already-loaded slot. The harness
  adds no VRAM. Slot files are written to `--slot-save-path`: one KV snapshot per saved state
  (prefix + up to 4 personas) per repetition, each roughly the KV size of about 1,100 tokens
  (tens of MB for small models, more for large ones or f16 KV). Budget **under 1 GB** for a full
  run; the owner should check free disk first.
- The harness's own memory is negligible (buffers a few hundred KB of results).

## Impact on live users
The model slot is unavailable to other traffic for the whole run (see preconditions). Live chat,
RAG and the other harnesses must be paused; noevia chats sharing the endpoint will stall or
evict the cache and corrupt the run. Schedule at low traffic. No Diary, OCR or code-sandbox
involvement; no user data; all prompts are synthetic.

## Outputs
Under `--out`, never overwritten (the harness refuses to reuse existing files):
- `results.json`: config, server facts (`/props`), every request row, summary, and any skipped arm.
  A mid-run abort still writes it, with an `aborted` field and the rows so far.
- `summary.md`: the markdown tables plus placeholders for the owner's decision.
Suggested location: `experiments/persona-kv/results/<date>-<model>/` (copy in only if the owner
wants the result recorded in the repo).

## Cleanup and rollback
The harness writes only under `--out` and, through llama.cpp, slot files named
`noevia-persona-kv-<run-id>-{prefix,astra,sol,jev,luna}.bin` in `--slot-save-path`. It never
touches `models.ini`, `.env`, compose files or any server config. Rollback: stop the harness
(Ctrl-C); the slot cache is transient. Afterwards the owner deletes the slot files (llama.cpp has
no delete endpoint), removes `--slot-save-path` if it was added only for this run and resumes
paused inference. The final slot state is the last request's cache; the next chat request simply
re-prefills.

## What the owner must approve
1. The model preset and the maintenance window (pausing chat/RAG/other harness runs; no backup or
   mover overlap).
2. Adding `--slot-save-path` to the llama.cpp launch for the run, and where it points.
3. Smoke first, then the full run with the parameters above (or changed bounds).
4. The adopt / revise / defer wording recorded afterwards; the harness records no decision.

## Limits of the study
- One slot, one model, synthetic prompts with an about 1k-token prefix; results on longer real
  contexts, several slots, or with a KV type/quantisation change are not covered.
- Tokenisation is boundary-sensitive: the persona sits after `\n\n`, so a token that straddles
  the prefix/persona boundary can shorten reuse by a token; this is measured, not corrected.
- Restore time is disk-bound and depends on `--slot-save-path` storage (SSD vs array); state where
  it lives in the report.
- Prompt quality of each persona is not evaluated, only cost.
