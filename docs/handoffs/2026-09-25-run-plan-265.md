# Run plan — issue #265: evaluate bounded Skill and toolbox selection on held-out tasks

## Host
DaServer (Unraid), public URL `https://noevia.daserver.work`. Sidecars per `docs/deployment.md`:
`cowork-web-1`, `cowork-diary-1`, `cowork-ocr-1`, native llama.cpp, embeddings, kiwix,
model-loader, code-sandbox, docling, Laya. The offline contract (#19) needs **no live model** to
run its own tests, but #265 explicitly calls for "authorized held-out models," so this plan adds
one real local-model pass on top of the existing offline harness, run from inside `cowork-web-1`
against the native llama.cpp endpoint (same access pattern as #264), never a new container.

## Configuration
- Containers: `cowork-web-1` only, calling the already-running native llama.cpp server. No Diary,
  OCR, code-sandbox involvement — the offline contract's own README states it "does not... start
  an MCP/script process."
- Env: no feature flags flip; skill/toolbox selection stays default-off in production
  (`enabled: false` per `experiments/system-one/skills-mcp/README.md`). For the model-backed run,
  reuse whatever `RESEARCH_BASE_URL`-style env the harness needs to point at the local endpoint —
  **the harness as currently written (`run.cjs --run-offline`) only accepts scripted answers, no
  endpoint/credential options** ("refuses to run without `--run-offline`, accepts no
  endpoint/credential/external fixture options"). This is a real gap: **the repo does not yet have
  a model-backed runner for this experiment** — see Open questions.
- GPU/VRAM/model: none for the pure offline contract tests (deterministic JS, no inference). For
  any live-model pass, same single-slot constraint as #264 (llama.cpp capped at 14GB, one model at
  a time on DaServer).

## Cases / fixtures
Synthetic only, already built: `experiments/system-one/skills-mcp/fixtures.cjs` — 8 development +
8 held-out-labelled synthetic cases, covering exact/no/overlapping matches, disabled/stale skills,
missing requirements, unready/unselected servers, dependency/budget/collision cases, malformed/
duplicate/cross-project IDs, timeout/error/cancellation, and malicious (prompt-injection) content
treated strictly as data. Never real project skills, real MCP servers, or real Diary content.

## Memory and duration estimate
- Offline contract/runner tests: pure Node `--test`, no model. Basis: existing baseline in
  `docs/research-skills-mcp-loading.md` ("the repository suite passed 1,247/1,247", now 1,487 per
  the 2026-09-24 roadmap entry) — well under a minute, negligible memory.
- `run.cjs --run-offline`: 8+8 fixtures × 3 modes × 3 repeats = 144 scripted records — seconds.
- Live-model pass (not yet scripted anywhere in the repo): estimated by analogy only, using the
  decisions pilot's per-call latency (`experiments/system-one/decisions/run.cjs`, cold
  start/RSS/latency per decision) and the routing-labels doc's 0.45–1.1s per small decision:
  144 calls ≈ **10–30 minutes** of model wall time. Not a measurement of an existing script.

## Impact on live users
Offline contract/unit tests touch no live system — zero impact. Any live-model pass shares
DaServer's single-model-slot constraint (see #264's plan): it occupies the local inference slot,
potentially queuing or evicting live chat/RAG requests needing the same model. No model needs
unloading in advance; the harness loads its own. Schedule at low traffic, and never concurrently
with #264's live pass (both would compete for the one model slot).

## Smoke test that runs first, and its pass criterion
Run the existing offline suite first, unmodified:
```sh
node --require ./apps/web/tests/hermetic-network.cjs --test experiments/system-one/skills-mcp/*.test.cjs
```
**Pass criterion:** all tests pass (matching the repo's existing green baseline — 1,487/1,487 per
`docs/roadmap.md`'s 2026-09-24 status, or the subset in this directory). If this fails, stop before
attempting any live-model extension, since the contract is the safety boundary the live run must
sit behind.

## Exact commands / scripts
```sh
# 1. Smoke: offline contract tests (existing, safe to run anywhere, including locally)
node --require ./apps/web/tests/hermetic-network.cjs --test experiments/system-one/skills-mcp/*.test.cjs

# 2. Offline scripted-answer harness (existing)
node experiments/system-one/skills-mcp/run.cjs --run-offline > /tmp/noevia-skills-mcp-$(date +%Y%m%d).jsonl
```
No existing script performs step 3 (a live-model-backed selection pass) — see Open questions. This
plan does not propose writing one now; it flags the gap for the owner to decide whether new
harness code is in scope before any model-backed run, per doubt about exceeding "the offline
contract exists" as sufficient justification (explicitly disallowed by the issue's Done-when).

## Outputs and where they are stored
- Offline suite: standard Node test-runner pass/fail output, not persisted unless the owner wants
  it archived.
- `run.cjs --run-offline` output: JSONL with fixture/set/config/catalogue hashes, opaque hashed
  IDs, bounded reason codes, actual body/schema byte counts, estimated schema tokens, local
  harness latency — excludes task text, descriptions, skill bodies, arguments, credentials (per
  the harness README). Store at `/tmp/noevia-skills-mcp-<date>.jsonl`, or copy into
  `experiments/system-one/skills-mcp/results.md` if the owner wants it recorded permanently.
- Any live-model results: new file analogous to `experiments/system-one/decisions/results/`, with
  a `summary.md`.

## Pass/fail criteria (from issue's "Done when")
- Report task completion, correct Skill/tool selection, schema/body token cost, latency,
  fallbacks, and unauthorized-action count across repeated runs. Note: `instructionAdherence`,
  `taskCompletion`, and `measuredTokens` are explicitly `null` in the current offline harness per
  its own README ("Instruction adherence, task completion and measured tokens remain null.") — so
  **this Done-when item cannot be satisfied by the offline harness alone**; it requires the
  live-model extension flagged above as a gap, with owner sign-off before writing it.
- Keep Skill script execution and each MCP candidate behind separate qualification gates (already
  true: `execution.test.cjs` and `compatibility.md`'s per-candidate adopt/defer/reject decisions
  are untouched by this plan).
- Record an adopt, revise, or defer decision, plus rollback conditions. Do not enable production
  selection solely because the offline contract exists (explicitly restated per the issue text;
  this plan does not enable `enabled: true` anywhere).

## Rollback / off switch
The skills/toolbox selector stays `enabled: false` by default in the library; nothing in this plan
changes that default or wires the experiment into chat. No `.env` or compose change occurs, so
there is no live rollback needed for the offline portion. For any live-model pass, rollback is
simply stopping the harness process; no persistent state is written to production.

## What the owner must approve
1. Whether a live-model extension to this harness should be built at all before evaluation can
   proceed (see the gap above) — this is a scope decision, not just a run-approval.
2. Which local model to use for any live-model pass, and the evaluation budget/window (avoiding
   overlap with #264's run, since both would need the single model slot).
3. Confirmation that no MCP candidate installation, script execution sandbox, or new dependency is
   in scope for this evaluation — only selection-contract quality on existing fixtures.
4. The final adopt/revise/defer wording before it's recorded in the repo or issue.

## Open questions (not found in repo)
- **No existing script runs this experiment's selection logic against a real, authorized local
  model.** `run.cjs --run-offline` only accepts scripted/injected answers, by design ("Injection
  is a test seam, not a sandbox for arbitrary JavaScript"). Building a live-model runner (analogous
  to `experiments/system-one/decisions/run.cjs`) appears to be new work, not something this plan
  can just "run" — flagged as an open question for the owner rather than assumed in scope.
- No repo doc states which model class the owner would authorize for this specific gate (unlike
  #264, which has a named prior model). This must be asked or decided before a live pass.

## Update 2026-09-25: live-model runner now exists (exact commands)
The gap in "Open questions" has been closed in code (it has not been run): `experiments/system-one/skills-mcp/live.cjs`
compares `baseline`, `embedding` (rules/embedding) and `system-one` (bounded proposals) on
synthetic tasks from `live-fixtures.cjs`, against an explicitly passed OpenAI-compatible endpoint.
It records task completion, selection and tool-choice correctness, endpoint-usage tokens
(including measured schema+body tokens), latency, fallbacks and unauthorized actions for each run, and writes
`results.jsonl` plus `summary.md`. It never executes Skill scripts or tools; the MCP catalogue is fake.

```sh
# 1. Smoke (includes the mocked-endpoint tests for live.cjs)
node --require ./apps/web/tests/hermetic-network.cjs --test experiments/system-one/skills-mcp/*.test.cjs
# 2. Config/fixture validation, no endpoint call
node experiments/system-one/skills-mcp/live.cjs --dry-run --base-url "$SKILL_EVAL_BASE_URL" --model "$SKILL_EVAL_MODEL"
# 3. Approved live pass from inside cowork-web-1 against native llama.cpp (base URL and model set by the operator)
node experiments/system-one/skills-mcp/live.cjs --base-url "$SKILL_EVAL_BASE_URL" --model "$SKILL_EVAL_MODEL" \
  --repeats 3 --seed 265 --out /tmp/noevia-skill-eval-$(date +%Y%m%d)
```
Default load: 8 tasks × 3 repeats × (3 arms + 1 bare call + 1 selection call) = 120 chat calls
(`--dry-run` prints the count). Env names: `SKILL_EVAL_BASE_URL`, `SKILL_EVAL_MODEL`, and `SKILL_EVAL_API_KEY`
(optional). None has a default. Model choice and the run window are still owner approvals 2 and 4.
